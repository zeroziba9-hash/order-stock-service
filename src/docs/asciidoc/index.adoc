이 문서의 HTTP 요청·응답과 필드 표는 실제 MySQL, Spring Security 필터, 서비스 트랜잭션을 거친 테스트에서 생성합니다.
필드 누락·미문서화 필드·타입 불일치가 발생하면 REST Docs 테스트가 실패합니다.
설명 문장과 아래 정책 표는 수동으로 관리하므로 정책 변경 시 함께 검토합니다.

== 읽기 전에

* 예제의 호스트는 로컬 Docker의 `http://localhost:18080`입니다. Java 직접 실행은 기본 8080입니다.
* 모든 금액은 원 단위 정수, 시각은 UTC ISO-8601(`Z` 접미사)입니다. ID·시각·상품은 테스트마다 달라집니다.
* `*.example.test` 계정은 테스트 전용입니다. 비밀번호·CSRF 토큰은 `<redacted>` / `<csrf-token>`으로 치환하고 `Set-Cookie`는 제거합니다.
* 실제 요청에서는 같은 브라우저/HTTP 클라이언트의 세션 쿠키(`JSESSIONID`)를 유지해야 합니다.
  MockMvc 테스트는 서버 세션을 직접 연결하므로 아래 HTTP 예제에는 세션 쿠키가 생략됩니다.
  브라우저의 같은 출처 `fetch` 또는 curl의 `-c cookies.txt -b cookies.txt`를 사용하세요.
* 회원가입은 자동 로그인이 아닙니다. `/auth/csrf` → 회원가입 → 로그인 → `/auth/csrf` 재조회 → 쓰기 요청 순서입니다.
  로그인 시 세션 ID와 토큰이 교체되므로 로그인 전 토큰을 재사용하지 마세요.
* 모의 결제·환불은 로컬/테스트용이며 실제 돈이 오가지 않습니다. 운영에서는 쓰기가 `404 MOCK_API_DISABLED`입니다.
  본인 결제·환불 이력 조회는 운영에서도 가능합니다. 설정을 먼저 확인하세요.
* 응답의 `X-Request-ID`는 서버가 매 요청 새로 발급하는 UUID입니다. 인증 거부·CSRF·요청 제한·500 응답에도 제공합니다.
  장애 문의 시 이 ID와 발생 시각으로 서버 로그를 찾습니다. 클라이언트가 보낸 같은 이름의 헤더는 신뢰하지 않습니다.
  주문 중복 방지용 `Idempotency-Key`와 별개이며, 같은 주문을 재시도해도 추적 ID는 달라집니다.

=== API 목록

[cols="1,3,1",options="header"]
|===
|메서드 |경로 |로그인
|GET |`/products`, `/storefront/config`, `/auth/csrf` |불필요
|POST |`/auth/register`, `/auth/login` |불필요, CSRF 필요
|GET |`/auth/me` |필요
|GET |`/auth/sessions` |필요, 본인 유효 접속 메타데이터만 조회
|POST |`/auth/password`, `/auth/sessions/logout-others` |필요, CSRF 필요
|POST |`/auth/logout` |CSRF 필요
|POST |`/orders` |필요, CSRF 필요
|GET |`/orders`, `/orders/{orderId}` |필요
|POST |`/orders/{orderId}/cancel` |필요, CSRF 필요
|POST |`/orders/{orderId}/payments`, `/orders/{orderId}/refunds` |필요, CSRF 필요, 모의 쓰기 허용 필요
|GET |`/orders/{orderId}/payments`, `/orders/{orderId}/refunds` |필요
|POST |`/admin/products/{productId}/inventory-adjustments` |ADMIN, CSRF·멱등 키 필수
|GET |`/admin/inventory-adjustments` |ADMIN
|GET, POST |`/admin/products` |ADMIN. POST는 CSRF·멱등 키 필수
|PUT |`/admin/products/{id}` |ADMIN, CSRF·revision 필수
|GET |`/admin/inventory-movements?productId=1` |ADMIN
|GET |`/admin/products/{id}/changes?beforeId=100` |ADMIN
|===

운영 상태 확인 API(`GET /actuator/health`, `/actuator/health/liveness`, `/actuator/health/readiness`)는 배포 문서를 참고하세요.
헬스 응답은 이 문서의 필드 계약 검증 범위에 포함하지 않습니다.

=== 인증 요청 제한

CSRF 검증을 통과한 POST 인증 요청에 적용합니다. IP별 로그인 120회/분, 회원가입 60회/10분,
IP+정규화 이메일별 로그인 실패 5회/5분입니다. 진행 중 로그인도 실패 제한의 슬롯을 예약합니다.
제한 시 계정 존재 여부와 무관하게 아래 공통 응답을 반환합니다. `Retry-After`의 정수 초만큼 기다린 뒤 수동 재시도하세요.
단일 프로세스 메모리이므로 재시작 시 초기화됩니다. 여러 인스턴스의 공통 제한은 지원하지 않습니다.

=== 내 접속과 비밀번호 관리

로그인한 회원만 본인의 유효한 접속 메타데이터를 조회합니다. 현재 접속 우선·최근 활동순으로 최대 100개를 표시하며
세션 ID·쿠키·IP·브라우저 원문은 응답하지 않습니다. 접속 시작은 세션 생성 시각으로, 로그인 시각과 다를 수 있습니다.

operation::account-sessions[snippets='http-request,http-response,response-fields']

다른 기기 로그아웃은 현재 접속을 유지하고 같은 계정의 나머지 저장 세션을 삭제합니다. 반복 실행은 `204`입니다.

operation::account-logout-others[snippets='http-request,request-headers,http-response']

비밀번호 변경은 현재 비밀번호 확인 후 해시·인증 버전·세션 삭제를 한 트랜잭션에 저장합니다.
성공 `204` 뒤에는 현재 브라우저도 새 비밀번호로 다시 로그인해야 합니다. 잘못된 현재 값은 `400 CURRENT_PASSWORD_INVALID`,
동일한 새 값은 `400 PASSWORD_UNCHANGED`이며 변경하지 않습니다. 유효 세션과 CSRF가 필요합니다.
비밀번호 변경 요청에는 로그인과 같은 IP별 요청 한도와 IP·계정별 실패 한도를 적용합니다. `400` 입력 오류도 실패에 포함합니다.

operation::account-password[snippets='http-request,request-headers,request-fields,http-response']

=== 상품 검색과 기간별 이력

공개 상품 검색은 판매 중인 상품만 반환하며 기존 `GET /products` 배열 API는 유지합니다.
20개씩 조회하고 다음 페이지 여부를 반환합니다. 가격 정렬은 가격·ID로 순서를 정합니다.
페이지 사이에 상품이 수정되면 결과가 바뀔 수 있어 검색 조건 변경 시 첫 페이지부터 다시 조회합니다.

operation::admin-product-search[snippets='http-request,query-parameters,http-response,response-fields']

주문 상태·기간 조회는 현재 회원 소유 조건과 함께 적용합니다. 날짜는 한국 시간 기준이고 시작·종료일을 모두 포함합니다.
다음 주문 페이지에도 같은 조건과 `beforeId`를 전달합니다.

수동 조정·재고 원장·상품 수정 이력에도 선택한 상품·커서와 함께 `from`, `to` 날짜를 전달할 수 있습니다.
조회 기간과 관계없이 재고 잔액 대조는 전체 원장을 사용합니다.

operation::admin-history-dates[snippets='http-request,query-parameters,http-response']

=== 여러 상품 주문

`POST /orders/cart`는 로그인·CSRF·필수 멱등 키와 중복 없는 1~20종 상품을 받습니다.
상품 순서를 정규화해 같은 내용의 순서만 바뀐 재시도도 같은 주문을 반환합니다. 단일 상품 API와 키 공간을 공유하며
서로 다른 내용의 키 재사용은 거부합니다. 가격·합계는 서버에서 결정합니다.
하나라도 재고 부족·판매 중지·저장 실패·금액 초과이면 요청 키·주문·모든 상품 재고·원장을 함께 롤백합니다.

operation::cart-order[snippets='http-request,request-headers,request-fields,http-response,response-fields']

=== 저장 장바구니와 가격 확인 주문

`GET /cart`와 `PUT /cart`는 계정별 장바구니를 저장합니다. 전체 내용을 수정할 때 직전 `revision`을 보내며, 다른 접속에서 수정됐다면 `409 CART_CHANGED` 후 다시 조회합니다.
`POST /orders/cart/quote`는 최신 상품·단가·합계를 보여줍니다. `totalAmount`는 정확한 십진 문자열이며 재고를 예약하지 않습니다.
사용자가 금액을 확인한 뒤 `POST /orders/cart/checkout`에 `quoteId`와 필수 요청 키를 보냅니다. 10분 이내라도 상품 정보가 바뀌면 `409 QUOTE_CHANGED`로 재확인을 요구합니다.
이미 완료된 동일 키·확인 ID는 만료·상품 변경·확인 정보 정리 이후에도 기존 주문을 반환합니다. 같은 확인 ID로 다른 키를 보내면 새 주문을 만들지 않습니다.
기존 `/orders`·`/orders/cart`는 현재 서버 가격으로 주문하는 호환 API이며, 웹 화면은 확인 API를 사용합니다.

=== 상품 상세와 설명 관리

`GET /products/{id}`는 익명으로 판매 중인 상품의 현재 정보와 등록된 설명·규격을 조회합니다. 품절은 조회할 수 있으며 판매 중지·없는 상품은 404입니다.
관리자의 `GET /admin/products/{id}/content`는 현재 설명·규격·설명 버전을 반환합니다. `PUT`에는 세 필드를 모두 보내며 빈 문자열로 지울 수 있습니다.
오래된 설명 버전은 `409 CONTENT_CHANGED`로 거부합니다. 설명 저장과 변경 이력은 함께 커밋·롤백합니다. 변경 없는 저장은 새 버전이나 이력을 만들지 않습니다.
`GET /admin/products/{id}/content/changes`는 최대 20건과 다음 `beforeId`를 반환합니다. 이름·가격·판매 상태의 수정 버전과 독립적입니다.

operation::product-detail[snippets='http-request,path-parameters,http-response,response-fields']
operation::product-content-update[snippets='http-request,request-fields,http-response,response-fields']
operation::product-content-history[snippets='http-request,http-response,response-fields']

회원가입은 항상 USER입니다. 관리자는 웹 API로 지정하지 않으며, 운영자가 DB 접근 권한으로 기존 회원의 역할을 변경합니다.
역할 부여 후 다시 로그인해야 새 권한이 세션에 반영됩니다. 권한 회수 후에는 기존 관리자 세션도 이 API에서 거부합니다.

=== 수동 입고·폐기

상품 행을 주문과 동일하게 잠그고, 재고·변경 이력·요청 키를 한 트랜잭션에서 저장합니다.
조정 후 재고는 0~2147483647이어야 합니다. 실패하면 전체를 롤백합니다.

operation::inventory-adjust[snippets='http-request,path-parameters,request-headers,request-fields,http-response,response-headers,response-fields']

=== 응답 유실 뒤 같은 요청 재확인

키는 관리자별로 구분합니다. 상품·수량·양끝 공백을 제거한 사유가 같으면 최초 변경 결과를 반환합니다.
그 뒤 재고가 달라졌어도 최초 beforeStock/afterStock을 유지하며 다시 조정하지 않습니다.
같은 키에 다른 내용을 보내면 `409 IDEMPOTENCY_KEY_REUSED`입니다.

operation::inventory-replay[snippets='http-request,http-response,response-headers,response-fields']

상품 필터와 커서로 조회하며 페이지당 최대 20건입니다. 이력을 수정·삭제하는 웹 API는 없습니다.

== 관리자 상품과 전체 재고 이력

=== 관리자 상품 등록·수정

신규 상품은 재고 0개입니다. 상품 등록에 관리자별 멱등 키가 필수이며 재응답은 같은 productId를 반환합니다.
가격은 0~1000000000000원 정수입니다. 수정은 조회한 revision을 보내고, 다른 수정이 먼저 반영되면 `409 CATALOG_CHANGED`입니다.
수량 변경은 기존 수동 재고 조정 API를 사용합니다. 상품 삭제 API는 없습니다.

=== 상품 정보 변경 이력

V12 이후 실제 이름·가격·판매 상태 변경만 저장합니다. 상품 수정과 이력은 같은 트랜잭션입니다.
관리자 ID·UTC 시각·변경 전후 값을 보관하며 이메일은 반환하지 않습니다. 웹에서 수정·삭제할 수 없습니다.
양끝 공백 제거 후 같은 내용이면 revision과 이력을 유지합니다. 이 경우에도 오래된 revision은 409입니다.
최신순 20건과 다음 커서를 반환합니다. 상품 등록·재고 증감과 V12 이전 수정은 이 목록에 포함하지 않습니다.

operation::catalog-changes[snippets='http-request,path-parameters,query-parameters,http-response,response-fields']

=== 전체 재고 변동

V11 적용 시 현재 수량을 BASELINE으로 보관합니다. 적용 이전 이력을 소급 복원하지 않습니다.
이후 주문·취소·환불·자동 만료·수동 조정을 같은 트랜잭션에서 기록하며 중복 상태 전이는 추가 변동을 만들지 않습니다.
일치 여부는 커서 페이지와 무관한 전체 기록 합계로 계산합니다. DB 직접 변경은 기록되지 않으며 불일치로 감지할 수 있습니다.

== 주문

관리자가 판매 중지한 상품의 새 주문은 `409 PRODUCT_NOT_SELLING`으로 거부합니다.
이전 주문의 이름·가격은 보존하며 취소·환불·만료에 따른 재고 복구는 계속 허용합니다.

=== 멱등 키를 사용한 생성

회원별 주문 키는 `[A-Za-z0-9][A-Za-z0-9._:-]{0,63}` 형식입니다.
응답을 받지 못했을 때 같은 키·같은 상품·같은 수량으로 재시도하세요. 다른 주문에는 새 키를 사용합니다.
`expiresAt`은 생성 시 고정하며 기본 30분입니다. 설정을 바꿔도 기존 주문의 마감은 바뀌지 않습니다.

operation::order-create[snippets='http-request,request-headers,request-fields,http-response,response-headers,response-fields']

=== 같은 키 재시도

신규 생성은 `201`, 같은 내용의 재요청은 `200`과 `Idempotency-Replayed: true`입니다.
주문 재조회 시 현재 주문 상태를 반환하므로 취소·결제·만료 뒤에는 상태가 달라질 수 있습니다.

== 모의 결제와 전액 환불

주문별 키가 필수이며 결제와 환불 키 공간은 서로 독립적입니다. 형식은 주문 키와 같습니다.
`result`는 `SUCCESS` 또는 `FAILURE`입니다. `FAILURE`도 정상 처리한 시도 이력이므로 신규 응답은 `201`입니다.
`status`를 확인하세요. 결제 실패는 `CREATED`, 환불 실패는 `PAID`를 유지합니다.
같은 키·같은 결과 선택은 최초 이력을 `200`으로 반환하며 선택을 바꾸면 `409 IDEMPOTENCY_KEY_REUSED`입니다.
기록된 결제 키의 재요청은 결제 마감 후에도 최초 이력을 반환합니다. 새 결제 시도는 마감 검증을 받습니다.

== 상품 이미지

관리자 등록·교체는 `multipart/form-data`의 `file`과 `revision`을 받습니다.
JPEG·PNG 3MB 이하, 각 변 8000px 이하, 1600만 화소 이하만 허용합니다.
메타데이터를 제거하고 긴 변 1600px 이하의 JPEG로 저장하며 투명 영역은 흰색이 됩니다.
가격·설명 버전과 별도의 이미지 버전을 비교하고 충돌하면 `409 IMAGE_CHANGED`를 반환합니다.
공개 `GET /products/{id}/image?revision=N`은 판매 중인 상품의 해당 최신 버전만 반환합니다.
삭제 또는 오래된 버전은 `404 IMAGE_NOT_FOUND`이며, 성공 응답은 `image/jpeg`, ETag, `Cache-Control: no-cache`입니다.
관리자 이미지 파일은 `GET /admin/products/{id}/image/file?revision=N`으로 확인합니다.
이력은 `GET /admin/products/{id}/image/changes?beforeId=N`에서 최근 20건과 다음 커서를 반환합니다.

== 주문 요청 복구

가격을 확인한 뒤 전송 전에 본인 quote에 요청 키를 등록합니다. 재등록하면 최초 키·종류·장바구니 버전을 반환합니다.
등록된 키와 다른 checkout은 `409 CHECKOUT_KEY_CHANGED`입니다. 기존 API의 미등록 quote도 계속 사용할 수 있습니다.
복구 목록은 확인 기한 후 24시간 이내의 미확인 요청을 최신 기한부터 최대 100건 반환합니다.
`orderId`가 있으면 이미 주문됐고, 없으면 같은 quote·key로 checkout을 재전송하여 결과를 확인합니다.
목록 조회가 재고를 확보하거나 주문을 실행하지 않습니다. 기한·가격·판매·재고 검증은 checkout에 적용됩니다.
acknowledge는 완료된 주문을 취소하지 않습니다. 미사용 quote는 잠금 아래 닫혀 후속 checkout이 `409 CHECKOUT_CLOSED`가 됩니다.
주문 완료와 닫기가 동시에 실행되면 quote 잠금 순서에 따라 하나의 결과로 확정됩니다.
quote 정리 후에도 완료된 주문은 기존 멱등 키로 재조회할 수 있습니다.

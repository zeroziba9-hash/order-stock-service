# STOCKROOM 웹 프론트

Spring Boot가 `src/main/resources/static`의 HTML·CSS·JavaScript를 제공합니다.
추가 설치·프론트 개발 서버 없이 Docker 실행 후 `http://localhost:18080/`에서 사용합니다.
Java 직접 실행은 `http://localhost:8080/`입니다. 기존 `/products` JSON API는 그대로 사용합니다.

## 화면 구성

컬렉션 첫 화면은 넓은 풍경 배경, 큰 제목, 상품 목록과 소개 영역으로 구성합니다.
`editorial.css`는 `index.html`의 `.storefront`에 적용하며 관리자·비밀번호 복구·결제 결과 화면의 공통 스타일과 구분합니다.
배경은 로컬 WebP 두 크기로 제공하며, 불러오지 못하면 짙은 녹색 배경과 제목·이동 버튼을 유지합니다.
상품 이미지·설명·가격·재고는 기존 API를 사용합니다. 풍경 이미지를 실제 상품 사진으로 사용하거나 상품 자료에 저장하지 않습니다.
이미지 제작 정보와 화면 확인 기준은 [컬렉션 디자인](storefront-design.md)을 참고하세요.

## 화면과 사용 흐름

1. 컬렉션: 실제 상품·가격·남은 재고를 조회하고 구매 가능한 상품만 필터링합니다.
2. 로그인·회원가입: 이메일과 비밀번호를 입력합니다. 회원가입 후 입력한 정보로 로그인합니다.
3. 주문: 상품을 선택하고 수량·금액을 확인합니다. 성공하면 내 주문 화면으로 이동합니다.
4. 내 주문: 본인 주문을 최신순으로 20개씩 조회합니다. 이전 주문 더 보기로 이어서 조회합니다.
5. 상세: 주문 당시 상품명·가격·수량·주문 상태와 결제·환불 이력을 확인합니다.
6. 취소: 미결제 주문을 확인창에서 취소하면 서버가 재고를 한 번만 복구합니다.
7. 로컬 체험: 상세 화면에서 모의 결제와 모의 전액 환불을 체험합니다. 실제 돈은 오가지 않습니다.
8. 관리자: ADMIN 계정의 상단 재고 관리 메뉴에서 수량·사유를 확인한 뒤 수동 조정하고 변경 이력을 조회합니다.
9. 내 계정: 로그인 이메일·유효한 접속을 확인하고, 다른 기기 로그아웃과 비밀번호 변경을 실행합니다. [계정 정책](account-management.md)을 참고하세요.
10. 검색·장바구니: 상품명·구매 가능 여부·가격순 조회와 여러 상품의 함께 주문을 제공합니다. 주문 상태·한국 날짜, 관리자 재고 부족·기간 이력은 [조회·주문 정책](store-operations-expansion.md)을 참고하세요.
11. 상품 관리: 재고 관리의 상품 관리 링크에서 상품을 0개로 등록하고 이름·가격·판매 상태를 변경합니다.
12. 전체 원장: 재고 관리 화면에서 선택한 상품의 주문·복구·수동 변경과 현재 재고/원장 합계의 일치 여부를 확인합니다.

관리자 지정·회수와 재요청 복구는 [관리자 재고 안내](admin-inventory.md)에 정리했습니다.
관리자 수동 조정·상품 등록은 sessionStorage에 요청 키와 내용을 저장할 수 없으면 POST를 보내지 않습니다.
상품 등록 응답 유실은 새로고침 뒤 같은 키로 확인하며, 수정 충돌은 새로고침해서 최신 값을 확인합니다.
[상품 관리·전체 원장](catalog-and-ledger.md)에 API와 정책을 정리했습니다.

모의 동작의 표시 여부는 공개 `GET /storefront/config`의 두 boolean 값으로 결정합니다.
설정 조회 실패 시 버튼을 표시하지 않습니다. `prod`에서는 두 값이 false이고 서버도 모의 쓰기를 거부합니다.
토스페이먼츠 카드 테스트 결제·전액 환불은 [테스트 키 설정](toss-test-payments.md) 후 사용할 수 있으며 기본값은 비활성화입니다.
실제 토스 결제창·승인·환불의 외부 검증과 배송 처리는 아직 완료 범위에 포함하지 않습니다.
등록 이미지가 있으면 목록·상세에 표시합니다. 이미지가 없거나 불러오지 못하면 CSS 일러스트로 안내합니다.
상품 관리 화면에서 이미지를 등록·교체·삭제하고 변경 이력을 확인할 수 있습니다.
확인 주문은 서버에도 요청 키를 등록해 탭 종료 후 결과를 확인합니다. [이미지·주문 복구 정책](product-images-and-order-recovery.md)을 참고하세요.

## 세션과 오류 처리

- 같은 출처의 API를 호출하여 기존 세션 쿠키·CSRF 검증을 사용합니다. CORS 허용을 추가하지 않습니다.
- 변경 요청 직전에 `/auth/csrf`에서 토큰을 가져옵니다. 로그인 시 세션·토큰 교체를 따릅니다.
- 비밀번호나 인증 토큰을 localStorage·sessionStorage에 저장하지 않습니다.
- 주문·모의 결제·환불의 요청 키만 사용자 ID와 요청 내용별로 sessionStorage에 임시 보관합니다.
  서버 응답을 받지 못했을 때 같은 내용으로 재시도하면 같은 키를 사용하며, 성공하면 삭제합니다.
  스토리지 사용이 막힌 브라우저에서는 현재 페이지 메모리로 대체합니다.
- 변경 요청을 자동 재전송하지 않습니다. 탭 종료·스토리지 삭제 후 결과가 불명확하면 내 주문부터 확인합니다.
- 요청 중 제출 버튼을 비활성화하며 회원가입·주문 처리 중에는 해당 창을 닫지 않습니다.
- 응답의 상품명·이메일 등 문자열을 HTML에 넣기 전에 이스케이프합니다.
- 로딩·빈 목록·통신 실패·재고 부족·로그인 만료를 화면에 표시합니다.
- 키보드 포커스·입력 라벨·본문 바로가기·상태 알림·반응형 배치를 제공합니다.

## 내 주문 목록 API

```http
GET /orders
GET /orders?beforeId=123
```

로그인이 필요합니다. 서버가 세션의 회원 ID를 사용하므로 다른 회원 ID를 지정할 수 없습니다.

```json
{
  "orders": [],
  "nextBeforeId": null
}
```

`orders`는 기존 주문 상세와 같은 응답의 배열입니다. 20개를 초과하는 경우 `nextBeforeId`를 반환하며,
다음 요청의 `beforeId`에 전달합니다. 양의 정수가 아닌 커서는 400입니다.
본인 주문 ID를 최대 21개 조회하고 해당 페이지의 항목만 가져와 컬렉션 fetch와 페이지 처리를 분리합니다.

## 검증

MySQL 통합 테스트에서 다른 회원 주문 제외, 22개 주문의 커서 페이지 경계, 빈 목록, 잘못된 커서,
익명 접근 차단, 정적 파일 공개와 모의 기능 설정을 검사합니다.
Docker CI는 컨테이너 재생성·DB 복원 후 주문 목록도 원본과 비교합니다.
HTTPS CI는 운영 프론트 제공, 주문 목록 인증과 모의 기능 비활성화를 검사합니다.
브라우저에서는 회원가입·로그인·수량별 주문·취소·모의 결제·환불·재로그인과 모바일 배치를 확인합니다.
이 흐름의 자동화와 실패·중복 요청 검증은 [브라우저 테스트 안내](browser-tests.md)를 참고하세요.

## 키보드와 접근성

본문 바로가기, 화면 이동 시 제목 포커스와 문서 제목 갱신, 로그인·주문 첫 입력 포커스,
확인창의 Tab/Shift+Tab 순환과 Escape 취소, 닫은 뒤 호출 위치 복귀를 제공합니다.
입력이 비활성화되거나 호출 버튼이 사라진 경우 현재 화면의 제목으로 복귀합니다.
[접근성 검사](browser-tests.md)는 자동 검사와 키보드 흐름을 확인하며 스크린리더 실사용 검증을 대신하지 않습니다.

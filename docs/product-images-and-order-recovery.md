# 상품 이미지와 주문 요청 복구

## 상품 이미지 관리

관리자는 `/catalog.html`에서 상품을 선택해 이미지를 미리 보고 등록·교체·삭제합니다.
등록 이미지가 있으면 목록과 상세에 표시하고, 없거나 불러오지 못하면 기본 일러스트를 표시합니다.
설명·규격이 없는 상품에 내용을 추측해 넣지 않습니다.

- JPEG·PNG만 허용하며 확장자 대신 실제 디코더로 파일 내용을 확인합니다.
- 원본은 최대 3MiB, 각 변 8000px 이하, 전체 1600만 화소 이하입니다. 크기를 먼저 확인한 뒤 디코딩합니다.
- JPEG의 EXIF 방향을 반영하고 긴 변 1600px 이하로 줄여 JPEG로 다시 인코딩합니다. 투명 영역은 흰색으로 합성합니다.
- 원본 파일명·경로·EXIF 위치 정보 등 메타데이터를 보관하거나 공개하지 않습니다. 애니메이션·SVG·WebP는 지원하지 않습니다.
- 상품당 이미지 하나를 저장합니다. 교체 전 원본 이미지를 따로 보관하는 기능은 없습니다.

`GET /admin/products/{id}/image`는 `{revision, imageUrl, width, height}`를 반환합니다.
`POST`는 multipart `file`과 직전 `revision`, `DELETE`는 쿼리 `revision`을 받습니다.
관리자 세션·CSRF와 현재 DB 역할을 검사합니다. 판매 중지 상품도 관리자 파일 경로에서 확인할 수 있습니다.
이미지 버전은 가격·판매 상태·설명 버전과 독립적입니다. 오래된 수정은 `409 IMAGE_CHANGED`로 거부합니다.
같은 정규화 결과나 빈 이미지 삭제는 버전과 이력을 추가하지 않습니다.

`GET /admin/products/{id}/image/changes?beforeId=N`은 최근 변경 20건과 다음 커서를 반환합니다.
변경 전후 SHA-256·버전·관리자·UTC 시각을 이미지와 같은 트랜잭션에 기록합니다.
이력 저장 실패 시 이미지 바이트·버전도 함께 롤백합니다.

공개 이미지 URL은 `/products/{id}/image?revision=N`입니다. 판매 중인 상품의 해당 최신 버전만 제공합니다.
오래된 URL·삭제된 이미지·판매 중지 상품은 404이고, 응답은 JPEG·ETag·`Cache-Control: no-cache`·`nosniff`를 사용합니다.
목록 API에 추가된 `imageUrl`은 등록 이미지가 없으면 null입니다. 목록 이미지 메타데이터는 한 번에 조회하며 BLOB은 목록에 읽지 않습니다.

V20의 `product_images`에 정규화한 JPEG를 저장합니다. 현재 단일 이미지·소규모 카탈로그에서는 DB 백업 한 번으로
상품 정보와 이미지의 일관된 스냅샷을 만들 수 있습니다. 파일 볼륨이나 외부 저장소의 별도 복원 순서가 필요하지 않습니다.
`product_image_changes`는 변경 메타데이터만 보관합니다. 사진 수·용량이 커지면 DB 크기·백업 시간을 측정해 외부 저장소 전환을 검토합니다.
[백업 도구](backup-restore.md)는 `--hex-blob`을 사용하며 복원 CI에서 실제 업로드 결과의 정확한 바이트와 이력을 비교합니다.

## 탭을 닫은 뒤 주문 결과 확인

가격과 수량을 확인한 뒤 checkout 전 `PUT /orders/cart/quote/{id}/intent`에 `{key, kind, cartRevision}`을 저장합니다.
`kind`는 `cart` 또는 `direct`이고, cart는 확인 당시 장바구니 수정 버전이 필수입니다.
최초 등록 이후에는 다른 탭이 새 키를 제안해도 최초 키·종류·장바구니 버전을 반환합니다.
등록된 키와 다른 checkout은 `409 CHECKOUT_KEY_CHANGED`로 거부합니다.
등록만으로 주문을 만들거나 재고를 확보하지 않습니다.

`GET /orders/cart/recovery`는 본인의 미확인 요청을 반환합니다.
확인 기한 후 24시간 이내만 최신 기한부터 최대 100건 표시하며, 상품명은 현재 이름이고 가격·수량은 확인 당시 값입니다.
타인의 quote 등록·닫기는 404, 익명 조회는 401입니다.
V21 이전 확인 요청은 키를 추정해 새 복구 기록으로 만들지 않습니다.

화면은 자동 주문하지 않습니다. 완료된 요청은 **주문 보기**, 미완료 요청은 구성·가격을 다시 보여준 뒤 **같은 요청으로 확인**합니다.
기한·상품 가격·판매 상태·재고 검증은 기존 checkout에서 다시 수행합니다.
완료된 요청의 재전송은 기존 주문을 반환하며 재고를 추가로 차감하지 않습니다.
장바구니 비우기는 저장된 장바구니 버전으로만 시도해 다른 기기의 변경을 보존합니다.

**이 요청 종료**는 quote 행을 잠그고 닫습니다. 먼저 완료된 주문은 취소하지 않으며 내 주문에 남습니다.
닫기가 먼저 끝난 미사용 quote는 이후 checkout을 `409 CHECKOUT_CLOSED`로 거부합니다.
checkout과 닫기가 경합해도 같은 quote 잠금으로 순서가 결정되고, 일부 항목만 차감되지 않습니다.
확인 완료·닫기 이후 목록에서 숨기며 원래 주문 요청의 완료 연결은 보존합니다.
quote 정리 후에도 완료된 주문은 원래 요청 키로 재조회할 수 있습니다.

브라우저는 sessionStorage에도 요청을 먼저 저장해 등록 응답 유실을 처리합니다.
서버 등록 전에 탭을 닫은 요청은 전송되지 않았으므로 서버 복구 목록에 없습니다.
기존 V17 보류 요청은 원래 본문·키로 재시도하며, 서버 복구는 새로 등록한 확인 주문부터 제공합니다.
서버 요청은 25초 후 기다림을 끝내지만 서버의 처리 취소를 의미하지 않습니다. 불확실한 쓰기는 기존 키를 유지합니다.

## 검증 범위

MySQL 통합 검증은 이미지 형식·크기·방향·정규화·버전·동시 수정·이력 실패 롤백,
주문 복구 소유권·최초 키 보존·재전송·닫기 경쟁·CSRF를 검사합니다.
데스크톱·모바일 브라우저에서는 이미지 등록·미리보기·교체 충돌·삭제·이미지 실패 fallback,
완료 응답 유실 후 저장소 삭제·다른 세션의 미완료 요청 재개·요청 종료·검색 조건 초기화를 검사합니다.
V19→V21 및 V21→V22 실제 앱 업그레이드에서 기존 로그인·쿠키·CSRF·업무 데이터를 보존하는지 확인합니다.
별도 빈 MySQL 볼륨 복원은 실제 업로드 바이트·이미지 이력과 완료/미완료 복구 요청까지 비교합니다.
공개 서버·외부 백업 저장소에서의 복원은 아직 검증하지 않았습니다.

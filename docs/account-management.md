# 계정·비밀번호·접속 관리

웹 화면 상단의 **내 계정**에서 로그인 이메일과 유효한 접속을 확인하고 비밀번호를 변경합니다.
회원 본인의 세션만 다루며 관리자 역할도 다른 회원의 접속을 조회·종료하는 권한을 제공하지 않습니다.

## API와 화면

| 요청 | 동작 |
|---|---|
| `GET /auth/sessions` | 본인의 유효한 접속 메타데이터 조회 |
| `POST /auth/sessions/logout-others` | 현재 접속을 제외한 같은 계정의 모든 저장 세션 삭제, `204` |
| `POST /auth/password` | 현재 비밀번호 확인 후 새 비밀번호 저장과 모든 세션 종료, `204` |

로그인이 필요하며 두 POST는 현재 세션의 CSRF 토큰이 필요합니다.
요청 본문으로 회원 ID나 세션 ID를 지정하지 않습니다. 대상 회원과 현재 세션은 서버에서 결정합니다.
비로그인 GET은 `401`, CSRF 없는 POST는 인증 확인보다 먼저 `403`이 반환될 수 있습니다.

접속 조회 응답은 `sessions`와 `truncated`입니다. 각 행은 `current`, `createdAt`, `lastAccessedAt`, `expiresAt`만 포함합니다.
현재 접속을 먼저 표시하고 이후 최근 활동순이며 최대 100개입니다. 초과 시 `truncated=true`이고,
다른 기기 로그아웃은 목록에 표시되지 않은 접속도 종료합니다. 만료된 행은 정리 작업 전에도 목록에서 제외합니다.
세션 ID·쿠키·CSRF·인증 BLOB·IP·User-Agent는 반환하지 않습니다.

`createdAt`은 세션 생성 시각으로 로그인 전 익명 세션 생성 시각일 수 있어 화면에는 **접속 시작**으로 표시합니다.
최근 활동·만료는 조회 시점에 DB에 저장된 값입니다. 조회 요청 자체의 활동은 응답 후 저장되므로 조금 늦게 보일 수 있습니다.
브라우저별 접속을 표시하며 물리 기기를 식별하거나 기기 이름을 수집하는 기능은 아닙니다.

화면은 두 변경 작업 전에 확인창을 띄웁니다. 다른 기기 로그아웃은 반복 실행해도 `204`이며 현재 접속과 다른 회원은 유지합니다.
접속 조회 실패 시 변경 버튼을 비활성화하고 새로고침으로 복구합니다. 만료된 계정의 정보는 화면에서 비웁니다.
비밀번호는 브라우저 저장소에 저장하지 않고 서버 요청 완료·확인 취소·화면 이동·로그아웃 후 입력란을 비웁니다.

## 비밀번호 변경 규칙

```json
{"currentPassword":"<현재 비밀번호>","newPassword":"<새 비밀번호>"}
```

새 비밀번호는 가입과 같이 8~72자, UTF-8 기준 72바이트 이하이며 공백만 사용할 수 없습니다.
대소문자·공백을 구분하고 현재 비밀번호와 다른 값을 사용합니다. 현재 비밀번호도 72바이트를 넘길 수 없습니다.
화면의 새 비밀번호 확인은 입력 실수를 막는 용도이며 서버에는 두 필드만 보냅니다.

| 결과 | 응답·상태 |
|---|---|
| 현재 비밀번호 불일치 | `400 CURRENT_PASSWORD_INVALID`, 해시·버전·접속 유지 |
| 새 값이 현재 값과 동일 | `400 PASSWORD_UNCHANGED`, 변경 없음 |
| 길이·자료형·필수 값 오류 | `400 INVALID_REQUEST`, 변경 없음 |
| 요청·실패 한도 초과 | `429 AUTH_RATE_LIMITED`, `Retry-After` 이후 수동 재시도 |
| 변경 성공 | `204`, 모든 접속 종료·현재 쿠키 만료, 새 비밀번호로 로그인 필요 |

비밀번호 변경은 [인증 요청 제한](auth-limits.md)의 로그인용 요청 한도를 별도 endpoint 버킷으로 사용합니다.
로그인과 IP·이메일별 실패/진행 중 검사 버킷은 공유합니다. `400` 입력 오류도 실패로 세고 성공하면 실패 수를 초기화합니다.
현재 비밀번호 불일치는 유효한 로그인 자체를 종료하지 않습니다. 응답 유실 시 자동 재전송하지 않고 새 비밀번호 로그인으로 확인합니다.

## 트랜잭션과 인증 회수

Flyway V14는 `app_users.auth_version`을 기본 0으로 추가합니다. 기존 회원 값과 세션 표를 지우지 않습니다.
`AuthenticatedUser`의 직렬화 UID를 유지하고 새 버전 필드를 추가해 이전 V13의 주체는 버전 0으로 읽습니다.

비밀번호 변경은 회원 행을 잠그고 현재 인증 버전·비밀번호를 확인한 뒤 BCrypt 해시 교체·인증 버전 증가·전체 세션 삭제를
같은 JPA/JDBC 트랜잭션에 저장합니다. 실패하면 함께 롤백하며 동시 변경 중 최대 한 건만 성공합니다.
성공 후 현재 HTTP 세션과 SecurityContext를 무효화합니다.

인증된 요청은 DB의 현재 버전과 저장된 주체의 버전을 비교합니다. 비밀번호 변경 전에 시작된 로그인이 나중에 세션을 저장해도
이전 버전은 다음 인증 요청에서 무효화됩니다. 사용자 삭제도 같은 방식으로 거부합니다. DB 장애 때 버전 확인을 생략하지 않습니다.
세션 삭제는 속성 cascade를 사용하며 이전에 읽은 세션의 활동 시각 저장으로 삭제한 접속을 새로 만들지 않습니다.

변경 전에 이미 인증 검사를 마치고 진행 중인 다른 업무 요청을 소급 취소하지 않습니다.
다른 기기 로그아웃이 끝난 뒤 새로 로그인하는 접속은 유효하며, 해당 기능은 비밀번호를 바꾸지 않습니다.
열린 다른 브라우저의 화면은 다음 API 요청에서 만료를 확인합니다. 실시간 화면 전송 기능은 포함하지 않습니다.
인증 버전 확인에 DB 조회가 추가되므로 향후 부하 측정에서도 이 비용을 포함합니다.
V13→V14 순차 교체는 검증하지만 구버전·신버전 혼합 운영과 구버전 앱으로의 롤백은 인증 회수 정책을 별도로 검증해야 합니다.

## 검증

실제 Tomcat·MySQL 테스트는 본인/타인/만료 접속·100개 한도·속성 cascade·현재 접속 보존·예전 쿠키 거부,
현재 비밀번호 오류·UTF-8 경계·CSRF·동시 변경·DB 쓰기 후 롤백·뒤늦게 저장된 이전 인증·요청 제한을 확인합니다.
REST Docs는 세 API 계약을 생성하고 현재·새 비밀번호를 마스킹하며, 마스킹 누락 시 문서 생성을 거부합니다.
데스크톱·모바일 Chromium은 확인 취소·비밀번호 확인·오류 복구·다른 접속 종료·전체 종료·새 비밀번호 로그인을 검증합니다.
기존 V13 이미지에서 생성한 실제 로그인 쿠키·CSRF·직렬화 인증으로 V14 교체 뒤 접속을 유지하는지도 확인합니다.

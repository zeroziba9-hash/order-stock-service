# 검색·여러 상품 주문·운영 조회

## 상품과 주문 찾기

`GET /products/search?q=&available=false&sort=ID_ASC&page=0`은 판매 중인 상품을 20개씩 조회합니다.
응답은 `products`, `page`, `hasMore`입니다. 상품명 부분 검색은 최대 100자이며 `%`, `_`, `!`도 문자 그대로 검색합니다.
정렬은 `ID_ASC`, `PRICE_ASC`, `PRICE_DESC`이고 가격 동률은 ID 오름차순입니다. 페이지는 0~10000입니다.
기존 배열 응답 `GET /products`도 유지합니다. 검색·정렬·구매 가능 여부를 바꾸면 첫 페이지부터 조회합니다.
오프셋 페이지이므로 조회 사이에 상품·가격이 수정되면 결과가 이동할 수 있습니다. 화면은 중복 ID를 제거하며 최신 결과는 새로고침합니다.
상품 개수 표시는 현재 불러온 개수이며 전체 상품 수를 의미하지 않습니다.

`GET /orders?status=CREATED&from=2026-10-01&to=2026-10-15&beforeId=100`은 현재 회원의 주문만 조회합니다.
상태는 `CREATED`, `PAID`, `CANCELLED`, `REFUNDED`, `EXPIRED`이며 생략하면 전체입니다.
날짜는 한국 시간 기준 시작·종료일을 모두 포함하고 서버가 UTC 범위로 변환합니다. 날짜 역전·잘못된 상태·커서는 400입니다.
다음 페이지에도 같은 검색 조건을 전달하며 화면의 조건 변경은 기존 결과와 커서를 초기화합니다.

## 관리자 운영 조회

`GET /admin/products/search?q=&selling=&lowStock=5&page=0`은 현재 DB의 관리자 권한을 확인하고,
판매 중지 상품을 포함해 상품명·판매 여부·재고 상한을 필터링합니다. 재고 상한은 0~1000000, 페이지당 20개입니다.
재고 화면에는 품절·5개 이하·10개 이하 필터, 상품 관리에는 판매 상태 필터를 제공합니다.
`GET /admin/products/{id}`는 진행 중인 조정 요청의 상품이 현재 페이지 밖에 있어도 동일 요청을 확인하기 위한 상세 조회입니다.

수동 조정 `/admin/inventory-adjustments`, 전체 원장 `/admin/inventory-movements`, 상품 수정 `/admin/products/{id}/changes`에는
기존 상품·커서와 함께 `from`, `to`를 전달합니다. 날짜 규칙은 주문과 같으며 페이지를 넘겨도 유지합니다.
원장의 현재 재고·기록 합계·정합성 비교는 선택한 날짜의 일부 행이 아닌 **전체 원장**으로 계산합니다.

## 장바구니와 여러 상품 주문

장바구니는 로그인 회원별로 이 탭의 sessionStorage에 저장하며 다른 회원의 장바구니를 표시하지 않습니다.
담는 것만으로 재고를 확보하지 않고 최종 가격·재고는 주문 트랜잭션에서 결정합니다. 수량 변경·빼기를 지원합니다.
예상 합계는 브라우저의 BigInt로 계산해 큰 수량도 정수 정밀도를 유지합니다.

`POST /orders/cart`는 필수 `Idempotency-Key`, 세션 인증·CSRF와 아래 본문을 받습니다.

```json
{"items":[{"productId":1,"quantity":2},{"productId":2,"quantity":1}]}
```

상품은 중복 없는 1~20종, ID·수량은 양의 정수입니다. 순서를 ID로 정규화한 내용의 SHA-256을 요청 키와 함께 저장합니다.
같은 상품·수량의 순서만 바뀐 재전송은 같은 주문이며 다른 내용의 키 재사용은 409입니다.
단일 상품 API와 회원별 키 공간을 공유합니다. 과거 단일 상품 요청의 해시가 NULL이면 보존된 상품·수량에서 비교 값을 계산합니다.

상품을 ID 오름차순으로 잠그고 서버 가격의 곱·합을 오버플로 검사합니다. 요청 키·하나의 주문·모든 항목·재고·상품별 원장을
한 트랜잭션에 저장합니다. 하나라도 부족·판매 중지·금액 초과·저장 실패면 모두 롤백합니다.
기존 취소·전액 모의 환불·자동 만료도 같은 상품 잠금 순서로 모든 항목을 한 번씩 복구합니다. 부분 취소·부분 환불은 제공하지 않습니다.

화면은 요청 전에 본문과 키를 저장합니다. 응답이 불확실하면 장바구니 편집을 잠그고 새로고침 뒤에도 같은 요청을 확인합니다.
성공하면 장바구니·보류 요청을 비웁니다. 저장소를 사용할 수 없으면 요청을 보내지 않습니다.
탭 종료·저장소 삭제 후에는 키를 복구할 수 없으므로 새 주문 전에 내 주문을 확인합니다.

## 반복된 성능 비교 실패 수정

진단 버전에서 실제 `409 ORDER_CONFLICT`, MySQL `40001 / 1213` 교착을 재현했고 요청 추적 ID로 응답과 로그를 연결했습니다.
DB의 교착 기록에서는 `products.PRIMARY`와 미완료 주문 요청의 `uq_order_requests_order` 인덱스가 함께 나타났습니다.
대기 중 요청이 nullable 유니크 완료 인덱스에 들어간 상태로 상품을 기다리고, 상품을 가진 요청이 완료 인덱스를 바꾸면서 순환했습니다.

V16은 완료 연결을 `order_request_completions`로 옮깁니다. 요청당 하나의 완료 연결과 주문당 하나의 연결은 PK·유니크·FK로 유지하며,
미완료 요청에는 완료 인덱스 행이 없습니다. 기존 연결을 먼저 복사한 뒤 이전 nullable 열·인덱스를 제거합니다.
요청 키와 연결은 기존 트랜잭션에 참여하며 요청 삭제 시 연결도 cascade로 삭제합니다.
V17은 장바구니 내용 해시 열을 추가합니다. 과거 요청 키·주문과 항목·재고 값을 새 주문으로 다시 만들지 않습니다.

수정 후 CI와 같은 동시성 4·워밍업 32·측정 64·두 차감 방식·집중/분산·3회 반복을 새 DB 세 곳에서 수행했습니다.
36개 측정 구간의 성공 주문 2,304건·워밍업 1,152건과 원장·취소 후 복구를 확인했습니다. 성공 응답 기준과 부하를 낮추지 않았습니다.
실패 시에는 상태별 개수·고정 오류 코드·서버 발급 UUID만 별도 JSON에 기록하며 응답 본문·헤더 원문·쿠키·비밀번호는 저장하지 않습니다.
CI는 실패 JSON과 안전한 앱 로그를 보존하며 실패한 구간의 성능 결과는 보고하지 않습니다.

## 시간대와 업그레이드 주의

기간 검증에서 한국 시간 JVM의 기존 Hibernate Timestamp 경유 저장이 UTC DATETIME을 9시간 앞당기는 것을 재현했습니다.
`hibernate.type.java_time_use_direct_jdbc=true`로 LocalDateTime을 JDBC 4.2로 직접 읽고 써 앱·JDBC 원장·Flyway의 UTC 값을 일치시킵니다.
[Hibernate 설정 설명](https://docs.hibernate.org/stable/core/javadocs/org/hibernate/cfg/MappingSettings.html#JAVA_TIME_USE_DIRECT_JDBC)을 참고하세요.
CI는 UTC JVM의 locking과 Asia/Seoul JVM의 conditional에서 원본 DB 시각·응답 시각·한국 날짜 끝 경계를 검증합니다.

기존 UTC Docker 앱의 시각은 이 설정으로 변하지 않습니다. 과거 비UTC JVM에서 직접 Java로 저장한 데이터는
원본 DB 시각과 당시 JVM·연결 설정을 별도로 확인해야 합니다. JDBC로 쓴 이력과 혼재할 수 있어 일괄 시각 보정을 실행하지 않습니다.
V16은 이전 앱이 읽는 `order_requests.order_id`를 제거하므로 이전 이미지로 단순 롤백할 수 없습니다.
업그레이드 전 백업과 새 DB 복구를 준비하고 [공개 배포 준비](production-readiness.md)의 복구 절차를 사용합니다.

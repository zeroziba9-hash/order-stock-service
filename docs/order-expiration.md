# 미결제 주문 자동 만료

주문 생성 때 재고를 예약하고 결제 마감 시각을 저장합니다. 기본 마감은 생성 후 30분입니다.
미결제 주문이 기한을 넘기면 백그라운드 작업이 `CREATED → EXPIRED`로 전환하고 재고를 한 번만 반환합니다.
결제 완료·수동 취소·환불 완료 주문은 만료 처리하지 않습니다.

## API와 화면

주문 생성·상세·목록 응답에 `expiresAt`과 `expiredAt`이 추가됩니다. 두 값 모두 UTC ISO-8601 시각입니다.
`expiresAt`은 주문 생성 시 고정한 결제 마감이며, `expiredAt`은 실제 처리 시각입니다.
만료 시 `cancelledAt`도 `expiredAt`과 같게 기록합니다. 주문·항목·요청 키·결제 실패 이력은 삭제하지 않습니다.

- 마감 직전까지만 새 모의 결제를 허용합니다. 마감 시각과 같거나 늦으면 `409 ORDER_EXPIRED`입니다.
- 작업 실행 전에는 상태가 잠시 `CREATED`여도 새 결제는 거부합니다. 다음 작업 또는 수동 취소 때 재고가 반환됩니다.
- 만료된 주문의 반복 `/cancel`은 기존 `EXPIRED` 결과를 반환하고 재고를 더하지 않습니다.
- 같은 주문 생성 키의 재시도는 만료된 기존 주문을 반환합니다. 새 주문에는 새 키를 사용합니다.
- 과거 결제 키의 재시도는 저장된 최초 결과를 반환합니다. 새로운 승인을 만들지 않습니다.
- 본인 주문·이력 접근 규칙은 유지합니다. 백그라운드 처리용 HTTP 엔드포인트는 추가하지 않았습니다.

웹 상세에는 결제 기한, 만료 후에는 “주문 만료”와 처리 시각을 표시합니다.
만료 주문의 결제·취소 버튼을 숨깁니다. 기한과 버튼은 상세를 조회할 때 계산하며 실시간 카운트다운은 제공하지 않습니다.
열어둔 화면의 기한이 지났더라도 서버가 최종 판단합니다. 늦은 결제 오류가 오면 주문·재고를 다시 조회합니다.
백그라운드 상태 변경은 내 주문의 새로고침 또는 화면 재조회로 확인합니다.

## 작업 주기와 트랜잭션

Spring의 fixed-delay 작업은 앱 시작 후 기본 60초 뒤에 첫 실행하고, 이전 작업 완료 후 60초 뒤에 다시 실행합니다.
한 번에 최대 100개의 만료 후보 ID만 결제 마감·주문 ID 순서로 읽습니다.
`(status, expires_at, id)` 인덱스를 사용하고 주문 항목 전체를 한 번에 가져오지 않습니다.

후보마다 별도 트랜잭션으로 주문 행을 잠근 뒤 상태·마감을 다시 확인합니다.
결제·수동 취소·다른 만료 작업도 같은 주문 잠금을 사용합니다.
만료를 반영할 때 상품 ID 순서로 상품 행을 잠그고 상태 변경·재고 복구를 함께 커밋합니다.
DB 오류나 재고 범위 초과가 발생하면 해당 주문의 변경을 모두 롤백합니다.
다른 후보는 계속 처리하며 실패한 주문은 다음 주기에 다시 시도합니다.

마감 즉시 실행을 보장하지 않습니다. 대량 대기·DB 잠금·실패 재시도로 재고 반환이 늦어질 수 있습니다.
실패 주문이 배치 전체를 채우면 뒤 주문이 지연될 수 있으므로 실패 로그와 대기량을 확인해야 합니다.
현재 단일 앱용 스케줄러이며 여러 앱이 실행돼도 행 잠금으로 중복 복구를 막지만 작업량은 중복됩니다.

## 설정

| 프로퍼티 | 기본값 | 허용 범위 |
|---|---|---|
| `app.orders.expiration.enabled` | `true` | 자동 작업 켜기·끄기 |
| `app.orders.expiration.payment-window` | `30m` | 1초~24시간, 신규 주문에 적용 |
| `app.orders.expiration.poll-interval` | `60s` | 1초~1시간 |
| `app.orders.expiration.batch-size` | `100` | 1~1000 |

ISO-8601 `PT30M`·`PT60S`와 `30m`·`60s` 단위를 사용할 수 있습니다. 잘못된 범위는 시작 시 거부합니다.
설정을 바꿔도 이미 저장된 주문의 마감은 바꾸지 않습니다.
`enabled=false`는 자동 작업만 끄며, 주문 마감 기록·기한 이후 새 결제 차단은 유지합니다.
일반 DB 통합 테스트에서는 작업을 꺼서 테스트 간 간섭을 막고, 전용 스케줄러 테스트에서만 켭니다.

## 기존 DB 업그레이드

Flyway `V9`가 기존 주문에 `createdAt + 30분`을 마감으로 채웁니다. 기존 주문 상태·재고는 마이그레이션 SQL에서 바꾸지 않습니다.
**기존의 오래된 미결제 주문은 새 앱의 자동 작업이 켜진 뒤 만료되고 재고가 반환됩니다.**
이전 버전에는 만료 상태가 없으므로 배포 전 백업과 주문 확인이 필요합니다.
새 스키마·새 상태를 이전 앱이 읽을 수 있다고 가정하지 않으며 앱 이미지만 되돌리는 롤백은 하지 않습니다.
이미 적용한 V1~V8 마이그레이션은 수정하지 않습니다.

## 검증

실제 MySQL 테스트에서 다음을 확인합니다.

- 저장된 마감과 UTC 응답, 마감 직전·정확한 마감의 처리, 늦은 결제 차단.
- 실제 스케줄러가 수동 호출 없이 짧은 기한의 주문을 만료하고 재고를 복구.
- 20개 동시 만료 요청, 만료·수동 취소 경쟁, 만료·늦은 결제 경쟁.
- 결제 완료·취소·환불 주문의 만료 제외, 멱등 재요청과 기존 실패 이력 보존.
- 실제 flush 후 오류의 전체 롤백, 한 주문 실패 시 다른 주문 처리, 다음 실행 재시도.
- 배치 수 제한·마감 순서, DB 제약, 만료 후 본인 접근 규칙.

```powershell
.\gradlew.bat test --tests '*OrderExpiration*'
```

[브라우저 CI](../.github/workflows/browser.yml)는 일반 14개 테스트 후 같은 일회용 프로젝트의 앱만
테스트 전용 [override](../.github/compose.expiration-test.yaml)로 재시작합니다.
이 단계에서만 마감 5초·주기 1초로 실행하고 데스크톱·모바일 각 1개 테스트가 실제 만료·재고 복구·화면·늦은 결제 거부를 확인합니다.
일반 앱이나 운영에 이 override를 적용하지 않습니다.

[업그레이드 CI](../.github/workflows/expiration-upgrade.yml)는 불변 커밋의 V8 앱으로 새 일회용 DB를 준비하고
기한 경과·기한 전·결제 완료·취소 완료·환불 완료 주문 5개를 실제 HTTP로 생성합니다.
같은 볼륨을 새 앱으로 올린 뒤 기존 주문의 30분 마감 보완, 오래된 미결제 주문만 만료,
재고 한 번 복구, 기존 이력·요청 키 보존을 확인합니다. 새 설정 7분은 신규 주문에만 적용되는지도 검증합니다.
테스트 계정 정보가 있는 임시 상태 파일은 결과 아티팩트로 업로드하지 않습니다.

구현 기준은 [Spring 스케줄링](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)과
[Spring Boot 설정 바인딩](https://docs.spring.io/spring-boot/reference/features/external-config.html)의 공식 문서를 참고했습니다.

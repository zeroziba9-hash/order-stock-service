# 카드 테스트 결제

토스페이먼츠 결제창의 카드 인증 → 서버 승인 → 전액 환불을 연결한다. 기본값은 비활성화이며, 현재 지원 범위는 **테스트 키·KRW·전액 승인 및 환불**이다. 실제 토스 계정이나 키 없이 수행하는 자동 검증은 가짜 SDK와 HTTP PG의 계약 검증이며, 실제 토스 결제창·카드 인증·외부 API 성공을 증명하지 않는다.

## 로컬 설정

1. 토스페이먼츠 개발자 센터에서 같은 테스트 애플리케이션의 **개별 연동 API 키** `test_ck_…`와 `test_sk_…`를 준비한다. 결제위젯 키 `test_gck_…`, `test_gsk_…`는 이 연결에 사용하지 않는다.
2. `toss.env.example`을 `.local/toss-test.env`로 복사하고 로컬 편집기에서 두 키를 채운다. 키를 채팅·커밋·스크린샷에 넣지 않는다. `APP_TOSS_ORIGIN`은 실제 접속 주소와 일치시킨다. `localhost`와 `127.0.0.1`은 서로 다른 출처다.
3. Windows 실행기를 사용한다면 `.local/launcher.json`의 기존 `composeFiles` 배열 마지막에 `"compose.toss.yaml"`을 추가하고 `start-server.cmd`로 다시 시작한다. 기존 프로젝트명·환경 파일·DB 볼륨을 유지한다. 직접 Compose를 쓰는 경우 기존 명령에 `-f compose.toss.yaml`을 추가한다.
4. 로그인하고 주문 상세에서 **테스트 카드 결제**를 누른다. 인증 후 결과 화면에서 승인 결과를 확인한다. 결제가 완료되면 주문 상세의 **테스트 전액 환불**로 취소한다.

결제사 호출은 서버에서만 이루어진다. 공개 설정 API는 활성화 여부만 반환하고, 주문 소유자에게만 결제창에 필요한 클라이언트 키와 고객 키를 제공한다. 시크릿 키는 브라우저로 전달하지 않는다. 리다이렉트 URL의 결제 인증 정보는 화면 진입 즉시 주소에서 지우며 웹 저장소에 저장하지 않는다. `prod` 프로필에서는 테스트 결제 활성화를 거부한다. 라이브 키, 실제 과금, 부분 환불, 가상계좌, 정기 결제는 제공하지 않는다.

## API

로그인이 필요한 변경 요청에는 기존 CSRF 토큰이 필요하다. `Idempotency-Key`는 결제 준비 요청에 사용한다. 같은 주문의 준비 중 결제를 재사용하며, 진행 중인 외부 결제는 하나만 허용한다.

| 요청 | 용도 |
| --- | --- |
| `GET /payments/toss/config` | 공개 활성화 여부, `mode=TEST` |
| `POST /orders/{orderId}/toss/checkout` | 주문 소유자만 결제 준비, 헤더 `Idempotency-Key` 필수 |
| `POST /payments/toss/confirm` | `{orderId: checkoutId, paymentKey, amount}` 인증 정보를 서버에서 검증 후 승인 |
| `GET /orders/{orderId}/toss` | 가장 최근 결제 상태, 없으면 `NONE` |
| `GET /payments/toss/states?ids=1,2` | 소유 주문 최대 20개의 최근 상태 일괄 조회 |
| `GET /payments/toss/{checkoutId}` | 해당 결제 시도의 결과 확인 |
| `POST /payments/toss/{checkoutId}/reconcile` | 조회 가능 시각이 지난 결제를 PG와 대조 |
| `POST /payments/toss/{checkoutId}/refund` | 승인된 결제 전액 취소 |
| `POST /webhooks/toss/payment` | 공개 알림 수신, 인증된 PG 조회를 앞당기는 힌트만 반영 |

여기서 `orderId`라는 토스 필드는 서비스 주문 번호가 아닌 서버가 생성한 `srp_…` 결제 준비 식별자다. 승인 금액은 준비 시 저장한 주문 금액과 같아야 한다. 응답의 `pending=true`이면 HTTP 202이며 성공 확정이 아니다. `reviewRequired=true`인 결제는 추가 승인·환불 요청 없이 PG 조회만 수행한다.

## 장애와 재고 처리

- 승인 의도와 PG 멱등 키를 먼저 커밋하고 DB 트랜잭션 밖에서 HTTP를 호출한다. 결과 반영 시 부모 주문 잠금과 작업 소유권을 다시 검사한다. 느린 PG 응답 동안 DB 잠금을 유지하지 않는다.
- `CONFIRMING`, `UNKNOWN`, `CANCELING` 동안 주문 취소·자동 만료·모의 결제 및 모의 환불을 차단한다. 외부 승인 여부가 불명확한 주문의 재고를 먼저 복원하지 않는다. 승인 시작이 만료 전이면 응답이 만료 후 도착해도 검증된 결과를 반영한다.
- 만료 처리 후보를 고를 때 확인 중인 결제를 제외한 뒤 배치 크기를 적용한다. PG 대기 주문이 앞에 몰려도 다른 미결제 주문의 만료가 밀리지 않는다. 결제사에서 승인 실패·유효 기간 만료가 확인되면 재고 예약 보호를 해제한다.
- 승인·환불마다 고정 PG 멱등 키를 사용한다. 재시작 후 먼저 PG를 조회하고 필요할 때만 같은 키로 재요청한다. 이 구현은 첫 요청 후 24시간까지만 변경 요청을 재시도한다. 이후에는 조회만 하며 운영 확인이 필요하다.
- 정상 승인만 기존 결제 이력과 주문 `PAID`를 함께 커밋한다. 검증된 전액 취소만 환불 이력·`REFUNDED`·재고 복구·재고 원장에 함께 반영한다. 중복 요청과 오래된 응답은 같은 재고를 두 번 복원하지 않는다.
- 금액·주문·통화·결제 방식 불일치와 부분 취소는 자동 처리를 멈춘다. PG에서 정상 스냅샷을 확인하기 전까지 재고 예약을 유지한다. 처리량은 작업당 최대 10건, 작업 임대 30초, 재조회 간격 10~300초다. 완료된 승인도 5분마다 대조해 결제사 관리자 화면의 전액 취소를 감지한다.
- 웹훅 본문은 16KiB까지 읽으며 주문별 힌트를 30초에 한 번만 반영한다. 웹훅의 상태·금액만 보고 주문을 변경하지 않는다. 외부에서 도달하는 HTTPS 웹훅 주소가 없어도 주기 조회로 복구한다.

## 백업 복원

`scripts/production-db.sh restore`는 복원된 결제를 `outbound_disabled=TRUE`로 바꾸고 진행 중 작업 임대를 해제한다. `READY`도 `UNKNOWN`으로 바꾼다. 백업 시점 이후 외부 승인이 있었을 수 있기 때문이다. 인증 키가 백업에 없으면 서버가 저장한 결제 준비 식별자로 PG를 조회한다. 원격 승인 또는 전액 취소가 확인될 때만 로컬 주문을 보정한다. 승인된 결과를 확인한 후에는 소유자의 새 전액 환불 요청을 받을 수 있다.

원격 결과가 없거나 불명확하면 자동 재승인하지 않고 재고를 유지한다. 실제 PG 대시보드와 주문 이력 대조가 필요하다. 현재 `prod`에서 테스트 결제를 켤 수 없으므로, 복원 검증은 DB의 조회 전용 전환과 테스트 프로필에서의 복구를 각각 확인한다. 운영용 결제 도입 시 라이브 키·정산·분쟁·데이터 복원 정책을 별도 설계해야 한다.

## 자동 검증 재현

전용 `order_stock_test` DB를 설정한 뒤 `./gradlew test --tests 'com.zeroziba.orderstock.payment.toss.*'`를 실행한다. MySQL과 루프백 HTTP 서버를 사용해 응답 유실·DB 롤백·중복 승인·환불·소유권·CSRF·메타데이터 불일치·복원된 결제의 조회 전용 복구를 검증한다. 테스트 정리 작업은 DB명이 다르면 삭제 전에 중단한다.

브라우저 CI는 일반·만료·인증 제한 단계 후 `.github/compose.toss-test.yaml`을 추가한 일회용 스택에서 `E2E_TOSS=true`로 실행한다. `pg-stub`는 명시적 테스트 프로필에서만 허용하며 실제 PG 호출과 혼용하지 않는다. SDK는 Playwright 경로 대체로만 주입된다. 결제창 계약·승인·환불·새로고침·응답 유실 복구·SDK 로딩 실패를 데스크톱과 모바일에서 확인한다. 테스트 네트워크 추적 파일은 저장하지 않는다.

# 앱·DB 중단과 주문 복구 검증

`scripts/verify-resilience.py`는 스스로 무작위 이름의 일회용 Compose 프로젝트와 빈 DB 볼륨을 만들고 루프백 18089 포트에서만 실행합니다.
기존 데모·운영 프로젝트 이름을 입력받지 않으며 기존 프로젝트·볼륨이 발견되면 연결하거나 삭제하지 않습니다.
비밀번호·쿠키·CSRF·회원·주문 본문·SQL 결과를 보고서에 넣지 않습니다.

```powershell
docker build -t order-stock-recovery .
python scripts/verify-resilience.py --disposable --image order-stock-recovery --duration-seconds 300 --output build/recovery-report.json
```

18089 포트가 비어 있고 Docker Compose·Python 3가 있어야 합니다. `--disposable`은 필수이며 실행 시간은 60~3,600초입니다.
테스트 시간이 더 필요하면 `--duration-seconds 1800` 또는 `3600`으로 실행합니다.

## 검사 내용

1. 실제 로그인·계정 장바구니·확인 주문을 만들고 앱을 SIGKILL로 종료합니다. 재기동 후 동일 로그인·장바구니·멱등 주문 결과·상품별 차감 1회를 검사합니다.
2. DB를 중단하고 준비 상태 503과 주문 불가를 확인합니다. 복구 후 같은 확인 정보·키의 주문 성공과 재전송 결과를 검사합니다.
3. 이 환경만 5초 결제 기한으로 잠시 재설정합니다. 주문 후 앱을 멈춰 실제 기한이 지나게 하고, 30분 기본 설정으로 다시 기동합니다. 이전 주문의 고정 기한과 모든 항목의 자동 만료·원장 복구 1회를 검사합니다.
4. 지정 시간 동안 두 상품 확인 주문·동일 요청 재전송·취소를 반복합니다. 최종 재고·전체 원장 합계와 미완료 요청 연결 0건을 확인합니다.

DB 중단 감지는 일회용 환경의 Hikari 연결 대기 2초에서 검증합니다. 운영 기본 대기 시간이나 운영 복구 시간을 측정한 결과가 아닙니다.
반복 검증은 확인 요청 제한 이내의 낮은 빈도로 실행하며 처리량 벤치마크로 사용하지 않습니다.
최종 보고서에는 실제 반복 시간·횟수·단계별 통과 여부와 일회용 환경 정리 여부만 저장합니다. 실패 시 실패 단계도 남깁니다.

[Recovery verification CI](../.github/workflows/resilience.yml)는 5분 반복 검사를 실행합니다.
5분 검사는 장기 운영 안정성의 보장이 아닙니다. 실제 운영 부하의 긴 관측·독립 부하 발생기·메모리/커넥션 변화 분석은 배포 환경에서 추가합니다.
공개 HTTPS·서버 밖 백업 복구는 이 검사에 포함하지 않으며 보고서의 해당 항목도 false로 유지합니다.
새 빈 DB로 백업을 옮기는 검사는 별도의 [백업·복원 검증](backup-restore.md)을 사용합니다.

## 로컬 확인 기록

2026-10-16의 일회용 MySQL 8.4·Docker Desktop 검사에서 세 가지 중단/복구 단계를 통과했습니다.
이후 실제 306.94초 동안 두 상품 주문·재전송·취소 43회를 완료했고 재고·원장 잔액과 요청 완료 연결이 일치했습니다.
끝난 뒤 이 검사에서 만든 앱·DB·볼륨을 제거했습니다. 이 기록은 로컬 환경의 제한된 복구 결과입니다.

# MySQL에 로그인 세션 저장

Spring Session JDBC로 로그인 상태와 CSRF 토큰을 MySQL에 저장합니다.
같은 DB를 사용하는 앱을 재시작·재생성해도 유효한 `JSESSIONID` 쿠키로 인증을 이어갑니다.
로그아웃하거나 30분 동안 사용하지 않은 세션은 재사용할 수 없습니다.

## 저장 구조와 설정

Flyway V13이 `app_sessions`와 `app_sessions_ATTRIBUTES` 두 InnoDB 테이블을 추가합니다.
기존 상품·회원·주문·재고·이력 테이블은 변경하지 않습니다. `_ATTRIBUTES` 대문자 접미사는
Spring Session의 표 이름 규칙을 따르며 Linux MySQL에서도 그대로 사용합니다.

| 저장 내용 | 설명 |
|---|---|
| 세션 ID·내부 기본 키 | 서버가 생성한 UUID. 쿠키와 DB 세션을 연결 |
| 생성·최종 접근·만료 시각 | epoch 밀리초. 기본 유휴 제한 1,800초 |
| principal name | 로그인 이메일. 기존 회원과 같은 최대 254자 |
| 세션 속성 | 인증 주체·권한 스냅샷·CSRF 토큰을 직렬화한 BLOB |

`spring.session.jdbc.initialize-schema=never`로 자동 DDL을 끄고 Flyway만 구조를 관리합니다.
Boot 4.0.8이 관리하는 Spring Session JDBC 4.0.5와 MySQL용 저장 쿼리를 사용합니다.
로그인 성공 시 인증 주체의 비밀번호 해시와 credentials를 지운 뒤 저장합니다.
BLOB은 암호화가 아닙니다. 세션 ID와 속성은 인증 정보이므로 DB·백업 접근 권한을 제한하고 로그·메트릭 라벨에 넣지 않습니다.

## 쿠키·CSRF·권한

- `JSESSIONID`, 경로 `/`, HttpOnly·SameSite=Lax를 유지합니다. `prod`는 Secure이며 HTTP로 보내지 않습니다.
- 로그인 성공 시 ID와 CSRF 토큰을 교체합니다. 로그인 전 쿠키·토큰은 사용할 수 없습니다.
- 앱 재시작만으로 ID·CSRF 토큰을 바꾸지 않습니다. 재시작 전 토큰도 유효한 같은 세션에서 사용할 수 있습니다.
- 로그아웃은 DB 세션·속성을 삭제하고 쿠키를 만료시킵니다. 이후 앱을 재생성해도 삭제된 쿠키는 인증되지 않습니다.
- 관리자 API는 저장된 역할뿐 아니라 현재 DB 역할도 확인하므로 권한 회수는 기존 세션에도 적용됩니다.
  세션에 저장된 역할 표시는 재로그인할 때 갱신됩니다.
- [계정 관리](account-management.md)의 비밀번호 변경은 모든 접속을 삭제하고 인증 버전을 증가시킵니다. 다른 기기 로그아웃은 현재 접속만 유지합니다.
- 브라우저 세션 쿠키이므로 브라우저 종료·쿠키 삭제 후 자동 로그인을 보장하는 기능은 아닙니다.

## 만료와 정리

기본 `server.servlet.session.timeout=30m`을 사용하며 마지막 접근 이후 유휴 시간을 기준으로 만료합니다.
요청 시 만료를 확인하므로 정리 작업 실행을 기다리지 않고 접근을 거부합니다.
만료 행 정리는 기본 매분 실행하며 `EXPIRY_TIME` 인덱스와 속성의 삭제 cascade를 사용합니다.

## 업그레이드와 복구

V12 이전의 메모리 세션을 DB로 옮기지는 않습니다. V13을 처음 적용할 때는 한 번 다시 로그인해야 합니다.
그 뒤 동일한 앱 버전과 DB로 재시작하면 세션이 유지됩니다. JDK 직렬화 형식이므로 인증 클래스나 의존성 버전이
달라지는 배포의 호환성은 별도로 확인해야 하며, 호환되지 않는 배포에서는 세션을 무효화하고 재로그인하도록 운영합니다.
V14 계정 기능은 기존 V13 이미지의 직렬화 인증·쿠키·CSRF를 유지하는 순차 업그레이드를 검증합니다.

일반 재시작과 백업 복원은 다릅니다. 과거 백업의 세션을 그대로 살리면 백업 이후 로그아웃한 쿠키가 다시 인증될 수 있으므로
[복원 도구](backup-restore.md)는 앱·프록시가 중지된 새 복구 DB에서 세션을 모두 지웁니다.
회원·주문과 세션 테이블 구조는 유지합니다. 수동 SQL 복원도 트래픽 연결 전에 `DELETE FROM app_sessions;`로 속성을 함께 삭제해야 합니다.
백업에는 세션 ID·인증 주체·CSRF도 들어갈 수 있으므로 신뢰할 수 있는 백업만 복원하며 접근 제한·암호화 보관이 필요합니다.

## 검증

- 실제 Tomcat·MySQL에서 ID 교체, 인증 속성 저장·해시 제외, 새 HTTP 클라이언트의 저장 세션 사용,
  로그아웃·쿠키 재사용 거부, 정리 전 만료 거부·속성 정리, 오래된 CSRF 거부, 현재 관리자 권한,
  동일 세션의 동시 24요청과 254자 이메일 저장을 확인합니다.
- 쿠키 테스트는 로컬·운영 Secure 설정과 HttpOnly·SameSite·경로·이름을 확인합니다.
- [Docker CI](../.github/workflows/docker.yml)는 원래 쿠키·CSRF를 보관한 뒤 앱·DB를 재생성하고 재로그인 없이 기존 주문을 재조회·재응답합니다.
  로그아웃 후 앱을 한 번 더 재생성해 오래된 쿠키가 거부되는지도 확인합니다.
- 백업 복원 CI는 원본에 실제 인증 세션이 있음을 확인하고 대상의 세션·속성이 비어 있으며 원래 쿠키가 HTTPS에서도 거부되는지 확인합니다.
  새로 로그인한 뒤 기존 데이터를 비교합니다. V8 업그레이드 CI는 V13 적용과 초기 세션 표가 비어 있음을 확인합니다.
- 기존 MockMvc 테스트는 연결한 MockHttpSession을 사용합니다. JDBC 테스트는 해당 프로필의 자동 구성 제외를 해제하고 실제 서블릿 필터·쿠키·DB를 사용합니다.

## 운영 범위

DB 읽기·쓰기가 추가되며 DB 장애 시 인증 요청도 실패할 수 있습니다. 메모리 저장소로 자동 우회하지 않습니다.
검증은 단일 앱의 재시작·재생성 범위이며 다중 인스턴스와 배포 버전 혼용은 별도 검증 대상입니다.
인증 요청 제한 버킷·JVM·주문 카운터는 계속 프로세스 단위이며 재시작 시 초기화됩니다.
기존 [성능 측정](paired-benchmark.md)은 기록된 커밋의 결과이며 JDBC 세션을 추가한 현재 버전의 처리량으로 해석하지 않습니다.
